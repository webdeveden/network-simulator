How NetSim fits together

Frontend, backend, Redis (rate limiting and caching) and monitoring (Prometheus + Grafana), step by step.

1. Big picture 2. Opening the app 3. Login + rate limit 4. Caching 5. Monitoring 6. Cheat sheet

1. The big picture

Every box is one container from docker-compose.yml, except your browser and you.

Top half = the app. Bottom half = watching the app. The app never talks to Prometheus or Grafana: Prometheus comes to it every 15 seconds and reads /metrics.

  • frontend (nginx) serves the built Vue files and forwards only /api/* to the backend.
  • backend (FastAPI) is the API. It reads and writes users and progress in Postgres, and uses Redis for login counters and cached copies.
  • Exporters translate Redis and Postgres stats into the same text format as /metrics.
  • Prometheus stores the numbers for 7 days and checks the alert rules. Grafana asks it questions in PromQL and draws the answers.

2. Opening the app: frontend and backend

What happens when you type localhost:8090 and the Missions page loads.

Why nginx in front? In production there's no Vite dev server. npm run build turns the Vue code into plain files in dist/, and nginx serves them very fast. nginx also forwards /api/* to the backend, so the browser and the API share one address, which avoids CORS problems. Anything that isn't a file, like /missions, gets index.html back (try_files), and Vue picks the page.

nginx looks up the name backend again every 10 seconds (resolver 127.0.0.11). Without that, recreating the backend container gives it a new IP and every API call fails with 502.

Files: frontend/nginx.conf (routing, cache headers, real IP) · frontend/src/lib/api.ts (baseURL: '/api') · backend/app/main.py (routers) · backend/app/security.py (JWT check)

3. Logging in, protected by Redis (rate limiting)

A wrong password. Redis counts failures per IP + username, and the 6th try within 15 minutes is refused.

4. Caching /api/progress in Redis (cache-aside)

Redis sits beside Postgres, not in front of it. The backend code decides: ask Redis first, and Postgres only on a miss.

  • The key contains the user id (cache:progress:user:132), so users never see each other's data.
  • The 10-minute expiry (EX 600) is a safety net in case an invalidation is ever missed.
  • DEL comes after COMMIT; the other way round, another request could re-cache the old rows.
  • Postgres is the source of truth. Wiping Redis loses nothing; the next reads are just misses.

Files: backend/app/routers/missions.py (list_progress, complete_mission) · backend/app/cache.py (cache_get / cache_set / cache_delete)
See it: DevTools → Network → click progress → Response Headers → x-cache

5. Monitoring: Prometheus collects, Grafana draws

Two separate jobs: scraping writes numbers on a timer, and PromQL reads them when asked.

PieceJobConfig
backend /metricspublishes the current totals as text (no history)backend/app/metrics.py, main.py (Instrumentator)
exporterstranslate Redis / Postgres stats into the same text formatdocker-compose.yml
Prometheusscrapes every 15s, stores numbers for 7 days, checks alert rulesmonitoring/prometheus/prometheus.yml, alerts.yml
Grafanastores no data: asks Prometheus in PromQL and draws the answermonitoring/grafana/ (data source, netsim.json)

rate() turns an ever-growing total into "how fast right now". Labels like result split one counter into several series; keep their values a small, fixed set (never usernames or IPs). /metrics isn't reachable through nginx, which only forwards /api/: only containers inside the Docker network can read it.
